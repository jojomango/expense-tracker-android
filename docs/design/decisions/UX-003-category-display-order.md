## 現況問題

SPEC §3.3 寫的預設支出分類順序是：飲食、交通、居住、購物、娛樂、醫療、其他。但截圖 04 與 19 顯示的是：交通、其他、娛樂、居住、購物、醫療、飲食。英文介面（截圖 28）順序相同。

原因（已對照程式碼）：`data/Daos.kt` 的 `CategoryDao.observeAll()` 是 `ORDER BY isDefault DESC, name ASC`，依資料庫存的名稱排序；實際結果是依中文字的字碼排，沒有語意。英文介面順序一樣，是因為資料庫存的名稱是中文。`E2E-1-first-launch.yaml` 的註解已記錄這個現象，並用 `swipe` 繞過。

結果：最常用的「飲食」排最後，「其他」排第二，使用者每次記帳都要多找一次。

## 決定

1. 預設分類依 SPEC §3.3 的順序顯示：支出為飲食、交通、居住、購物、娛樂、醫療；收入為薪資、獎金、投資。
2. 自訂分類接在預設分類之後，依建立先後排列。
3. **「其他」永遠固定在整個清單（支出、收入各自）的最後**，自訂分類插在「其他」之前（人類決定，見下方第 1 點）。
4. 順序在記帳頁網格與分類管理頁一致。
5. 切換語言不改變順序（順序跟分類代號走，不跟顯示名稱走）。

純排序行為，沒有視覺改動，狀態與深色模式、英文介面都無差異，不新增 token。

## 行為改變

分類的顯示順序會變，這是使用者看得到的改變。依人類決定新增 `sortOrder` 欄位（見下方第 2 點），會動到 SPEC §3.3 屬性表、Room migration、備份檔（選填欄位）。`TESTCASES.md` 目前沒有斷言分類顯示順序的測案，合約 PR 會新增。`.maestro/E2E-1-first-launch.yaml` 的繞行 `swipe` 應移除（見 UX-001「行為改變」）。

## 無障礙

不變。TalkBack 讀出順序跟著顯示順序，順序正確後反而更符合預期。

## 不在這次範圍

- 依使用頻率自動排序。
- 使用者手動調整分類順序（`sortOrder` 是前提，這次只建立欄位，不做調整介面）。
- 分類網格的尺寸與列數（UX-001）。

## 人類決定（2026-10-23）

1. 「其他」的位置：**選項 B，永遠固定在最後**，自訂分類插在「其他」之前。
2. 順序怎麼存：**選項 a，新增 `sortOrder` 欄位**。
   實作那邊補充的理由：分類目前沒有任何建立時間欄位，選項 b 只能靠 SQLite 內部的列號表示先後，
   而備份「取代」匯入時分類會依名稱順序重新寫入，順序會亂掉，所以選項 b 無法保證自訂分類的順序。
   舊資料與舊備份沒有 `sortOrder` 時的補值規則，在合約 PR 裡寫明。
3. 使用者改過名稱的預設分類：順序**仍跟代號走**，不因改名移動（照提案）。
